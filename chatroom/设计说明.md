# Scout Chat 设计说明

## 一、整体架构

本聊天室采用前后端分离架构：
浏览器（前端） ←→ FastAPI 后端 ←→ SQLite 数据库

- **前端**：负责页面展示、用户输入、消息显示。
- **后端**：负责接收消息、存储消息、广播消息。
- **数据库**：负责持久化存储聊天记录。

## 二、为什么用 WebSocket

普通 HTTP 请求是“请求一次，响应一次，然后断开”。聊天室需要实时收到别人发的消息，如果用 HTTP，只能让前端不停问后端“有新消息吗”，这叫轮询。

轮询的缺点：
- 浪费资源，大部分请求都是空的。
- 消息延迟高，取决于轮询间隔。

WebSocket 的优点：
- 一次握手，建立长期连接。
- 双方随时可以互相发消息。
- 实时性高，延迟低。

所以聊天室用 WebSocket 更合适。

## 三、消息流程

一条消息从发出到显示，经过这些步骤：

1. 用户在前端输入消息，点“发送”。
2. 前端通过 WebSocket 把消息发给后端。
3. 后端收到消息，先存入 SQLite 数据库。
4. 后端把消息广播给所有在线连接。
5. 所有前端收到消息，显示在页面上。

## 四、为什么用 SQLite

聊天室要求“刷新页面后消息还在”，所以消息必须存到硬盘上。

选择 SQLite 的原因：
- 零配置，一个文件就是一个数据库。
- Python 自带 `sqlite3` 模块，不需要额外安装。
- 适合小项目，不用装 MySQL 或 PostgreSQL。

数据库表结构：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER | 主键，自动递增 |
| sender | TEXT | 发送者名字 |
| content | TEXT | 消息内容 |
| timestamp | TEXT | 发送时间 |

## 五、断线重连与用户名记忆

### 用户名记忆

用户第一次输入名字后，前端把名字存进浏览器的 `localStorage`。刷新页面时，先从 `localStorage` 读名字，如果读到了就自动进入聊天室，不用重新输入。

### 消息历史

用户连上 WebSocket 后，后端会先把数据库里最近 50 条消息发给他，这样刷新页面也能看到之前的聊天记录。

## 七、关键代码说明

后端 main.py
init_db()：启动时创建数据库和表。

save_message()：收到消息后存入数据库。

get_messages()：读取最近 50 条消息。

ConnectionManager：管理所有在线连接，负责广播。

/ws：WebSocket 接口，处理消息收发。

前端 app.js
joinChat()：连接 WebSocket，进入聊天室。

sendMessage()：把消息发给后端。

addMessage()：把收到的消息显示在页面上。

## 八、已知问题与改进方向
没有用户密码验证，任何人输入名字就能进入。

没有消息撤回功能。

断线后需要手动刷新页面，没有自动重连。

消息没有分页，历史消息只显示最近 50 条。

后续可以加：

用户登录注册。

消息撤回。

自动重连。

分页加载历史消息。
